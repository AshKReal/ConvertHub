# SECURITY.md

Сознательные отступления от `AUTH-RULES.md` и параметры, которые он называет по смыслу, но не фиксирует
числом — обязаны попадать сюда тем же изменением, что их вводит (`AUTH-RULES.md` §3). Список, не эссе: одна
запись — одна причина, один файл, где это на самом деле обеспечивается.

## 1. `Secure` на refresh-cookie — только в `NODE_ENV=production`

**Что:** `AUTH-RULES.md` §2 требует refresh-токен «только в cookie `HttpOnly` + `Secure` + `SameSite=Lax`» без
оговорок. В деве кука выставляется без `Secure`.

**Почему:** `Secure`-кука не возвращается браузером на `http://localhost` вообще — локальная разработка (`pnpm
dev:api`/`pnpm dev:web`, оба по HTTP) сломалась бы полностью, не только стала бы менее защищённой. Продакшн
(017) — HTTPS, там `Secure` включается автоматически.

**Где:** `apps/api/src/modules/auth/auth.controller.ts#respond` — `secure: env.NODE_ENV === 'production'`.

## 2. Окно терпимости 10 секунд на повторное предъявление refresh-токена

**Что:** `AUTH-RULES.md` §2: «предъявление уже использованного токена — кража: завершить всю цепочку сессий»,
без исключений. Спека 007 (решение владельца) вводит исключение: непосредственно предыдущий (только что
заменённый ротацией) токен в течение 10 секунд не считается кражей.

**Почему:** `ARCHITECTURE.md` §7 отдельно называет эту гонку нерешённой: несколько вкладок браузера одного и
того же пользователя могут почти одновременно обновить токен, и без терпимости вторая вкладка предъявит уже
«использованный» токен и получит полный разлогин, хотя кражи не было. Клиентская очередь на параллельные `401`
(`AuthService.ensureFreshToken`) решает эту гонку только *внутри одной вкладки*, не между ними.

**Где:** `packages/shared/src/constants/limits.ts#REFRESH_REUSE_GRACE_SECONDS`, логика —
`apps/api/src/modules/auth/auth.service.ts#resolveRefresh`. Вне окна, либо токен старше непосредственного
предшественника — по-прежнему кража, все сессии пользователя отзываются.

## 3. Rate limit на `login`/`register` — временный in-memory

**Что:** `AUTH-RULES.md` §2 требует rate limit на логин/регистрацию как жёсткий инвариант. Реализация в 007 —
не настоящий распределённый лимит.

**Почему:** Redis-based token bucket — спека 012, ещё не начата (стадия 8, после auth-стадии 7). Тащить Redis
в 007 ради двух счётчиков дублировало бы работу, которую 012 всё равно сделает иначе (token bucket, не fixed
window). До 012: один процесс, состояние не переживает рестарт/деплой, не распределено между инстансами (сейчас
их и нет — деплой единственного инстанса, 017).

**Где:** `apps/api/src/common/rate-limit/fixed-window-rate-limiter.service.ts`, вызывается из
`auth.controller.ts` — 10 попыток / 10 минут, по хешу IP и (только `login`) по нормализованному email.

## 4. Параметры argon2id

**Что:** `AUTH-RULES.md` §2 называет алгоритм (argon2id), не параметры.

**Значение:** `memoryCost: 19456` (19 МиБ), `timeCost: 2`, `parallelism: 1` — минимальный профиль, который
OWASP считает приемлемым для argon2id при 1 потоке.

**Где:** `apps/api/src/modules/auth/auth.service.ts#ARGON2_OPTIONS`. Меняется только здесь — второго места,
где вызывается `argon2.hash`, в кодовой базе нет.

## 5. `requestPasswordReset` не ждёт отправки письма

**Что:** `POST /v1/auth/forgot-password` отвечает клиенту до того, как `MailService.send()` реально завершится
(`void mail.send(...).catch(...)`, не `await`).

**Почему:** синхронная отправка сделала бы ответ для существующего email ощутимо медленнее (реальный SMTP-раунд-трип),
чем для несуществующего (мгновенный no-op) — тот же тайминг-канал, что `login()` (007) уже закрыл сравнением с
dummy-хешем, только на другой операции. Инвариант «одинаковый ответ независимо от существования аккаунта»
(`TECH-SPEC.md` §8.5) касается и времени ответа, не только тела.

**Где:** `apps/api/src/modules/auth/account.service.ts#requestPasswordReset`. Побочный эффект: если процесс
упадёт сразу после ответа клиенту, письмо может не уйти — TTL токена (30 мин) и повторная форма «Забыли пароль»
уже дают способ повторить попытку, отдельного ретрая нет (`docs/AUTH.md`).

## 6. `google/callback` ловит все исключения сам, не отдаёт их `AllExceptionsFilter`

**Что:** `backend.md` требует не ловить исключение, если с ним нечего делать — пусть летит в глобальный фильтр.
`GET /v1/auth/google/callback` — единственное место в кодовой базе, где это правило сознательно нарушено: весь
метод обёрнут в `try/catch`, любая ошибка (несовпавший `state`, сбой обмена кода на токен, `OAUTH_ACCOUNT_CONFLICT`,
отказ пользователя на экране согласия Google) превращается в `302`-редирект на фронт, не в JSON-ответ.

**Почему:** маршрут — не JSON API, а точка, куда Google полной навигацией браузера приводит пользователя сам.
`AllExceptionsFilter` отдаёт `application/problem+json` — показать такой ответ в адресной строке браузера
нечем, пользователь увидел бы сырой JSON вместо формы входа. Здесь ЕСТЬ что делать с ошибкой: превратить в
понятный экран, а не потерять контекст.

**Где:** `apps/api/src/modules/auth/auth.controller.ts#googleCallback`/`resolveGoogleCallback`. Различает ровно
одну причину для текста пользователю (`OAUTH_ACCOUNT_CONFLICT` → `oauthError=conflict`, всё остальное →
`oauthError=failed`) — конфликт стоит объяснить отдельно (сказать вошедшему через Google, что этот email уже
занят паролем — не оракул чужого аккаунта, пользователь уже аутентифицирован через сам Google), остальные
причины (сеть, просроченный `state`, отказ Google) пользователю неотличимы и не обязаны быть.
