## Задача

Пользователь, забывший пароль, должен иметь способ его восстановить по email. Вошедший — сменить пароль и
удалить аккаунт целиком. Без этого 007 (сессия) и 020 (готовые экраны на моках) не доводятся до конца: вход
без пути назад при забытом пароле и профиль без работающей кнопки удаления — это заведомо неполный продукт.

`SPECS.md` числит зависимость от 008 — по факту реальная работа (сброс/смена пароля, удаление аккаунта) не
трогает OAuth/`identities`: «запрет отвязки последнего способа входа» — пункт чек-листа 008 (отвязка ОДНОГО
провайдера у аккаунта с несколькими), не этой спеки (удаление ВСЕГО аккаунта, независимо от числа способов
входа). Решение владельца — не ждать 008.

## Входит

- Восстановление пароля: запрос по email → одинаковый ответ независимо от существования аккаунта (`TECH-SPEC.md` §8.5)
- Токен восстановления ≥32 случайных байт, в БД только хеш, TTL 30 минут, одноразовый
- Смена пароля из профиля → завершение всех сессий + письмо-уведомление
- Удаление аккаунта — полное и необратимое: сохранённые файлы стираются из `Storage`, история конвертаций и
  сессии — каскадом вместе со строкой `users` (решение владельца — было `onDelete: Restrict`, 003 сознательно
  откладывала выбор)
- Подключение экранов 020 (`/forgot-password`, `/reset-password/:token`, профиль) к реальным эндпоинтам

## Не входит

| Что | Где будет |
|---|---|
| Восстановление через Telegram-код | Отложено вместе с провайдером — `AUTH-RULES.md` §5 |
| Повторный ввод пароля при удалении аккаунта | Решение владельца — не сейчас, матчит готовый UI 020 |
| Реальный список привязанных провайдеров, отвязка одного | 008 |
| Redis-based rate limit на `forgot-password` | 012 — временный in-memory лимитер, как `login`/`register` (007) |

## Поведение

- Запрос сброса на существующий и на несуществующий email → идентичный `200`, письмо уходит только на первый.
- Переход по ссылке из письма → форма нового пароля; невалидный/использованный/просроченный токен → отдельный
  экран «ссылка недействительна» со ссылкой запросить новую, не зависшая форма.
- Успешный сброс → экран успеха со ссылкой на `/login` (не логинит автоматически — так уже сделано в 020).
- Смена пароля в профиле с неверным текущим паролем → инлайн-ошибка под полем, сессия не сброшена.
- Смена пароля с верным текущим → все сессии завершены, локальный выход, редирект на `/login`.
- Удаление аккаунта → модалка подтверждения → сессия и все данные удалены необратимо, редирект на `/`.

## Ошибочные сценарии

| Ситуация | Что видит пользователь | Код |
|---|---|---|
| Ссылка сброса не существует/использована/просрочена | Отдельный экран «ссылка недействительна» | `INVALID_RESET_TOKEN` |
| Неверный текущий пароль при смене | Инлайн под полем «Текущий пароль неверен» | `INVALID_CREDENTIALS` |
| Больше 10 запросов сброса за 10 минут с одного IP/email | Тост | `RATE_LIMIT_EXCEEDED` |

## Критерии приёмки

- [x] `POST /v1/auth/forgot-password` для существующего и несуществующего email → идентичные `200` и время ответа
- [x] Письмо реально приходит в MailHog со ссылкой на `/reset-password/<токен>`
- [x] `POST /v1/auth/reset-password` с валидным токеном → новый пароль работает, старый — `INVALID_CREDENTIALS`
- [x] Тот же токен повторно → `INVALID_RESET_TOKEN`; просроченный (искусственно состаренный) — тоже
- [x] После сброса — все refresh-токены пользователя мертвы
- [x] `PATCH /v1/auth/password` с неверным текущим паролем → `INVALID_CREDENTIALS`, сессия жива
- [x] `PATCH /v1/auth/password` валидный → все сессии мертвы, включая ту, из которой пришёл запрос
- [x] `DELETE /v1/auth/account` с сохранённым файлом → файл реально пропадает с диска, все строки в БД пропадают, cookie очищена
- [x] Фронт: полный сценарий восстановления через реальное письмо в браузере, обе темы
- [x] `pnpm typecheck` и `pnpm lint` зелёные
- [x] `any` в диффе отсутствует
- [x] Секретов и HEX-цветов в диффе нет

## План

Полный план с обоснованиями и отвергнутыми вариантами — в истории сессии; здесь — выжимка реализованного.

### Подход

`PasswordResetToken` — тот же опаковый токен + SHA-256-хеш приём, что `RefreshToken` (007), без цепочки
ротации: это одноразовое действие, не сессия. `AccountService` (новый, `modules/auth/`) — Prisma + argon2 +
`MailService` + `Storage`, той же оркестрационной формы, что `AuthService`; переиспользует его
`ARGON2_OPTIONS`/`normalizeEmail` (экспортированы, не продублированы) и общий `generateOpaqueToken`/`hashOpaqueToken`
из `token.service.ts` (вынесены из `generateRefreshToken`/`hashRefreshToken`).

`requestPasswordReset` не ждёт `MailService.send()` — синхронная отправка была бы тем же тайминг-каналом, что
`login()` уже закрыл dummy-хешем, только на письме, а не на пароле.

`deleteAccount` — `onDelete: Restrict` → `Cascade` на `File`/`Conversion`/`RefreshToken` (решение владельца):
реальные файлы стираются из `Storage` до удаления строк (иначе теряется `storageKey`), остальное — один вызов
`prisma.user.delete()`.

Все четыре новых маршрута — в уже существующем `AuthController` (`/v1/auth`), не в отдельном контроллере: не
стоило переносить уже отгруженный `GET /me` ради единообразия путей.

### Отвергнутые варианты

См. `docs/SECURITY.md` (п. 5) и коммиты — сведены туда, не дублируются здесь третий раз.
