## Задача

Пользователь должен иметь возможность зарегистрироваться и войти по email и паролю, оставаться в системе после
перезагрузки страницы, и выйти. Без настоящей сессии экраны 019 (вход/регистрация) и шапка «вошёл/не вошёл»
работают только на локальном моке — ничего не сохраняется на сервере, файл гостя нельзя привязать к аккаунту.

## Входит

- Регистрация email + пароль
- Вход, единое сообщение «Неверный email или пароль» на любую причину отказа
- JWT access (15 мин, в памяти) + refresh (30 дней, cookie `HttpOnly`/`Secure` только в production/`SameSite=Lax`)
- Ротация refresh при каждом обновлении; повторное предъявление уже использованного токена — кража: все сессии
  пользователя завершаются (кроме окна терпимости ~10с на непосредственно предыдущий токен — решение владельца
  против гонки нескольких вкладок, `ARCHITECTURE.md` §7, `docs/SECURITY.md` п. 2)
- Клиентская очередь на параллельные `401` — несколько запросов не вызывают `/auth/refresh` больше одного раза
- Выход
- Минимальный `GET /v1/me` (`{id, email}`) — решение владельца в этой сессии: без него очередь на `401` нечем
  проверить вручную, ни один другой эндпоинт 007 не требует access-токен
- Подключение экранов 019 (вход/регистрация/выход) к реальным эндпоинтам
- Подключение `userId` в `conversion.controller.ts`/`files.controller.ts` (были `TODO(007)`) — гостевые маршруты
  остаются гостевыми, но теперь реально узнают вошедшего пользователя

## Поведение

- Регистрация с новым email + паролем ≥ 8 символов → сразу вошёл, редирект на `/`, шапка показывает email.
- Регистрация с уже занятым email → `409`, сообщение под полем email, форма не отправляется повторно.
- Вход с неизвестным email, с верным email и неверным паролем — оба дают один и тот же `401` и один и тот же
  текст над формой.
- После успешного входа/регистрации обновление страницы (`F5`) не разлогинивает — сессия восстанавливается
  тихим `refresh` из cookie при старте приложения.
- Выход — сбрасывает сессию локально и на сервере (кука очищается), шапка возвращается к «Войти».
- Кнопки Google/Telegram остаются мок-заглушкой (008 подключит по-настоящему) — визуально не изменились.

## Ошибочные сценарии

| Ситуация | Что видит пользователь | Код |
|---|---|---|
| Email уже зарегистрирован | Текст под полем email | `EMAIL_ALREADY_REGISTERED` |
| Неверный email или пароль | Единый текст над формой входа | `INVALID_CREDENTIALS` |
| Access-токен отсутствует/просрочен на `GET /v1/me` | Тихий `refresh` + повтор (не видно пользователю), либо разлогин, если и `refresh` не удался | `UNAUTHENTICATED` |
| Больше 10 попыток входа/регистрации за 10 минут с одного IP (или с одного email на входе) | Тост | `RATE_LIMIT_EXCEEDED` |
| Поле формы пустое / email не тот формат / пароль короче 8 символов при регистрации | Текст под конкретным полем (без сети) | — (019, не изменилось) |

## Критерии приёмки

- [x] `POST /v1/auth/register` с новым email → `200`, `{accessToken, user}`, `Set-Cookie: refresh_token` (`HttpOnly`, `SameSite=Lax`, без `Secure` в деве)
- [x] Повторная регистрация тем же email → `409 EMAIL_ALREADY_REGISTERED`
- [x] `POST /v1/auth/login` с неизвестным email и с верным email/неверным паролем → оба `401 INVALID_CREDENTIALS`, неотличимы по телу ответа; время ответа не выдаёт разницу (dummy-hash сравнение)
- [x] `GET /v1/me` без токена / с мусорным токеном → `401 UNAUTHENTICATED`; с валидным → `{id, email}`
- [x] `POST /v1/auth/refresh` без cookie → `401`, не `500`
- [x] Ротация: `refresh` дважды подряд одним и тем же токеном в пределах 10с → второй не 401 (окно терпимости), обе выдачи валидны; та же пара, но с паузой > 10с → второй `401`, и токен от первой выдачи тоже становится недействителен (все сессии пользователя завершены)
- [x] `POST /v1/auth/logout` → кука очищена, идемпотентен (работает и без cookie), последующий `refresh` тем же токеном → `401`
- [x] 3 параллельных запроса к `GET /v1/me` с протухшим/невалидным токеном → ровно один `POST /v1/auth/refresh` в сетевой панели, все 3 в итоге успешны (проверено через реальный `HttpClient` в браузере, не эмуляцией)

- [x] Гостевой `POST /v1/convert`/`GET /v1/files/{id}/download` продолжают работать без токена как раньше; с валидным токеном файл реально привязывается к `user_id`, скачивание чужого файла → `404`, не `403`

## План

### Подход

Полный план с обоснованиями, отвергнутыми вариантами и точным устройством ротации/окна терпимости — в истории
сессии; здесь — выжимка того, что реализовано.

`RefreshToken` — отдельная таблица (не JWT): опаковый токен, в БД только SHA-256 хеш, состояние ротации
(`usedAt`/`replacedById`) и отзыва (`revokedAt`) хранится там же, что даёт мгновенный полный отзыв при краже —
чего самоподписанный refresh-JWT не может без отдельного blocklist. `TokenService` (чистый, без Prisma) отвечает
за access-JWT и генерацию/хеширование refresh-токена; `AuthService` — за Prisma-оркестрацию и argon2, ничего не
знает про `Request`/`Response`/cookie (`ARCHITECTURE.md` §4.1) — cookie выставляет `AuthController`.

Ротация — `updateMany(WHERE usedAt IS NULL)`, не read-then-write, чтобы два одновременных `refresh` одним и тем
же токеном не оба посчитали его свежим. Окно терпимости 10с на непосредственно предыдущий токен решает гонку
между вкладками (`ARCHITECTURE.md` §7), не ослабляя реакцию на настоящую кражу (токен вне цепочки/окна — все
сессии пользователя отзываются).

`conversion.controller.ts`/`files.controller.ts` не используют `JwtGuard` — они вызывают
`TokenService.verifyAccessToken()` напрямую и тихо остаются гостем при любой проблеме с токеном: эти маршруты
никогда не требовали авторизации, 401 там был бы неверным поведением. `JwtGuard` — жёсткий 401, только для
`GET /v1/me`.

На фронте `AuthService` (`core/services`) сама вызывает `HttpClient` — не через отдельный `features/auth/data/*.api.ts`,
чтобы не создать запрещённую стрелку `core → features` (`frontend.md`). `auth-interceptor.ts` навешивает
`Authorization` и реализует 401→refresh→повтор через `AuthService.ensureFreshToken()` (single-flight,
`shareReplay(1)` + `finalize`).

### Отвергнутые варианты

| Вариант | Почему отвергнут | Когда вернёмся |
|---|---|---|
| `argon2` для refresh-токена, не только пароля | Токен генерируется системой, 256 бит энтропии — не подбираемый секрет; тот же довод, что `AUTH-RULES.md` §2 приводит для API-ключей/Telegram HMAC | — |
| `@nestjs/passport` + стратегии | Добавляет зависимость и слой абстракции ради того, что и так пришлось бы написать руками: `conversion`/`files` нужен паттерн «проверить токен, если он есть, никогда не отказывать», для которого в Passport нет штатной стратегии | Если появится третий провайдер (SAML и т.п.) и ручной код разрастётся |
| Блокировка по пользователю на время `refresh` вместо окна терпимости | Не решает гонку между вкладками: вторая вкладка к моменту разблокировки всё равно предъявляет уже использованный токен | — |
| Redis-лимитер на login/register сейчас | 012 ещё не начата, будет token bucket, не fixed window — тащить Redis в 007 дублирует работу | 012 |

### Риски и границы транзакций

Ротация обёрнута в `$transaction` с conditional `updateMany`; лост-рейс (0 затронутых строк) не считается
ошибкой — повторный проход через окно терпимости корректно находит выигравшую сторону. Массовый отзыв при краже
— отдельный `updateMany`, не в одной транзакции с ответом клиенту (не требуется атомарности с HTTP-ответом).
Полный разбор — `docs/SECURITY.md`.
