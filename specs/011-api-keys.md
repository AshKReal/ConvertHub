## Задача

Пользователь публичного API должен выпускать ключи, видеть их список, перевыпускать скомпрометированный и
отзывать ненужный — из веб-интерфейса, под своей сессией. Экран `/api-keys` (022) принят на моке: ключи
генерировались в браузере, никуда не сохранялись, «полное значение» было бутафорией. Без этой спеки публичный
API (012) нечем аутентифицировать, а сам экран остаётся витриной.

## Входит

- Выпуск ключа: полное значение показывается в ответе один раз; в хранилище — только необратимый хеш и
  префикс для отображения
- Список своих активных ключей (маскированные), дата выпуска, момент последнего использования (пока всегда
  «никогда» — заполняется в 012)
- Перевыпуск: старый ключ перестаёт действовать немедленно, в ответе — новое полное значение один раз
- Отзыв: ключ перестаёт действовать и пропадает из списка; повторный отзыв того же ключа — не ошибка
- Управление ключами доступно только под сессией пользователя, никогда по самому ключу (`TECH-SPEC.md` §8.1)
- Верхняя граница на число активных ключей у одного пользователя
- Подключение экрана 022 к реальным эндпоинтам вместо локального мок-стора

## Не входит

| Что | Где будет |
|---|---|
| Bearer-аутентификация по ключу, запись `last_used_at` при вызове API | 012 |
| Rate limit и идемпотентность по ключу | 012 |
| Разные лимиты/песочница для `test` против `live` | Не заявлено; формат несёт признак окружения, поведение одинаковое |
| Скоупы/права ключа (только чтение и т.п.) | Не заявлено, отдельной задачи нет |
| Срок годности ключа, напоминание о ротации | Не заявлено |
| Экран аудита отозванных ключей | 022 явно отклонил; список показывает только активные |

## Поведение

- Вошедший открывает `/api-keys`, ключей нет → пустое состояние с кнопкой выпуска.
- Нажимает «Выпустить» → сервер генерирует ключ, отвечает полным значением один раз → модалка показа, после
  закрытия строка появляется в списке замаскированной.
- Нажимает «Перевыпустить» → подтверждение → старый ключ немедленно недействителен, в ответе новое полное
  значение → та же модалка показа; в списке новая маска на месте старой строки.
- Нажимает «Отозвать» → подтверждение (danger) → строка исчезает из списка; ключ больше не пройдёт
  аутентификацию в 012.
- Отменяет любую модалку → ничего не меняется.
- Достиг предела активных ключей и жмёт «Выпустить» → отказ с понятным сообщением, ничего не создаётся.
- Неавторизованный на `/api-keys` → редирект на `/login` (маршрут уже за guard, 022).
- Полное значение ключа не появляется больше нигде: ни в списке, ни в логах, ни в повторном запросе.

## Ошибочные сценарии

| Ситуация | Что видит пользователь | Код |
|---|---|---|
| Перевыпуск/отзыв чужого или несуществующего ключа | Не раскрывает, какой из двух | `API_KEY_NOT_FOUND` (404) |
| `:id` в пути не в формате идентификатора | — (curl/API-клиент) | `API_KEY_NOT_FOUND` (404) — не отдельный `INVALID_PARAMETER`, чтобы «нет такого» и «кривой id» были неотличимы |
| Выпуск при достигнутом пределе активных ключей | Тост с числом предела | `API_KEY_LIMIT_REACHED` (422) |
| Любой маршрут `/v1/api-keys*` без сессии | — | `UNAUTHENTICATED` (401) |

## Критерии приёмки

- [ ] `POST /v1/api-keys` под сессией → `200`, тело содержит полное значение вида `ch_live_` + 32 символа и его
  маску; прямой SELECT строки в БД — сырого значения нет, `keyHash` ≠ значению, `maskedPrefix` = первые 12 символов
- [ ] Тот же ключ во втором `GET /v1/api-keys` приходит только маской, полного значения нет
- [ ] `POST /v1/api-keys/:id/reissue` → новое полное значение; `sha256(старое значение)` после этого не значится
  активным (помечен отозванным), новый ключ отличается целиком, не только префиксом
- [ ] `DELETE /v1/api-keys/:id` → `204`; повторный `DELETE` того же id → снова `204`, в БД один `revokedAt`
- [ ] `reissue`/`DELETE` вторым пользователем на чужой `id` и на несуществующем → одинаковый `404 API_KEY_NOT_FOUND`,
  чужая строка не тронута
- [ ] Выпуск (N+1)-го активного ключа при пределе N → `422 API_KEY_LIMIT_REACHED`, число ключей не изменилось;
  отзыв одного и повторный выпуск — проходит
- [ ] Любой из четырёх маршрутов без cookie сессии → `401`, не `500`
- [ ] В логах приложения при выпуске/перевыпуске нет полного значения ключа
- [ ] Фронт: `/api-keys` в браузере — выпуск, копирование полного значения, перевыпуск, отзыв, пустое состояние —
  на реальных ответах; список переживает F5; обе темы
- [ ] `pnpm typecheck` и `pnpm lint` зелёные
- [ ] `any` в диффе отсутствует
- [ ] Секретов и HEX-цветов в диффе нет

## План

### Решено с владельцем

1. **Предел активных ключей на пользователя — `MAX_ACTIVE_API_KEYS = 3`.** Достигнут предел → `API_KEY_LIMIT_REACHED`.
2. **`environment`** — enum `LIVE`/`TEST` в схему заводится, но выпуск всегда `live` (клиент окружение не
   выбирает, 022 селектора не имеет). `TEST` активируется, если появится песочница с иными лимитами.
3. **Перевыпуск и отзыв** — ключ неизменяемая строка. Выпуск = INSERT, перевыпуск = `revokedAt` старой строке +
   INSERT новой в одной транзакции, отзыв = `revokedAt`. UPDATE той же строки на месте отвергнут (ниже).
4. **`docs/AUTH.md`** — 4 новых маршрута дописываются в таблицу эндпоинтов (`AUTH-RULES.md` §3: ключи —
   механизм аутентификации, `TECH-SPEC.md` §8.1).

### Подход

Новый модуль `modules/api-keys/` — свой маршрут (`/v1/api-keys`) и своя сущность (`api_keys`), условие
`ARCHITECTURE.md` §4.1 выполнено. Три файла: `api-keys.module.ts`, `api-keys.controller.ts`, `api-keys.service.ts`.

**Модель `ApiKey` (Prisma).** `id` (ULID, `VarChar(26)`), `userId`, `keyHash` (`@unique`), `prefix` (для показа,
`ch_live_a1b2`), `environment` (enum `ApiKeyEnvironment { LIVE, TEST }`, сейчас всегда `LIVE`), `createdAt`,
`lastUsedAt` (nullable, пишет только 012), `revokedAt` (nullable). `onDelete: Cascade` от `User` — то же решение
владельца, что 008/009. `@@index([userId])`. Отдельная миграция `prisma migrate dev`.

**Ключ — неизменяемая строка, а не мутируемая запись.** Выпуск = INSERT. Перевыпуск = `revokedAt` старой строке
+ INSERT новой в `$transaction`. Отзыв = `revokedAt`. Кроме `revokedAt`/`lastUsedAt` ни одно поле не меняется
после создания — проще и аудит, и рассуждение «какой хеш был активен когда». `revokedAt IS NULL` — единственный
предикат «действует». Та же модель, что у `RefreshToken` (007).

**Генерация.** Чистая функция рядом с сервисом (как `generateOpaqueToken` в `token.service.ts`): `randomBytes` →
32 символа алфавита `[a-z0-9]` (набор из макета 022 и примера `TECH-SPEC.md` §7.1; ~165 бит). Полное значение =
`ch_` + `live` + `_` + 32 символа. `keyHash = sha256(fullValue)` hex — SHA-256, не argon2: `AUTH-RULES.md` §2
прямо предписывает SHA-256 для высокоэнтропийных ключей. `maskedPrefix` в ответе = `ch_live_` + первые 4 символа
случайной части (совпадает с полем `maskedPrefix` модели фронта, 022).

**Эндпоинты — все под `@UseGuards(JwtGuard)` + `@CurrentUser()`:**

```
GET    /v1/api-keys             список активных (revokedAt IS NULL), маска, без keyHash
POST   /v1/api-keys             выпуск  → { ...item, fullValue }  один раз
POST   /v1/api-keys/:id/reissue перевыпуск → { ...item, fullValue }  один раз
DELETE /v1/api-keys/:id         отзыв, 204, идемпотентно
```

Управление ключами — только по сессии; `ApiKeyGuard` здесь не участвует (его вводит 012). `TECH-SPEC.md` §8.1:
ключ не даёт доступа к вебу.

**Предел активных ключей** — `MAX_ACTIVE_API_KEYS` в `packages/shared/limits.ts`. Проверка
`count(revokedAt IS NULL) >= N` перед выпуском (не перед перевыпуском — там число не растёт).

**`packages/shared`:**

- `schemas/api-keys.ts`: `apiKeyEnvironmentSchema` (`z.enum(['live','test'])`), `apiKeyListItemSchema`
  (`id`, `environment`, `maskedPrefix`, `createdAt: string`, `lastUsedAt: string | null`), `apiKeyListResponseSchema`
  (`{ items }` — без курсора, ключей единицы), `issuedApiKeySchema = apiKeyListItemSchema.extend({ fullValue })`.
- `constants/error-codes.ts`: `API_KEY_NOT_FOUND` (404), `API_KEY_LIMIT_REACHED` (422).
- `constants/limits.ts`: `MAX_ACTIVE_API_KEYS = 3`.

**Фронт — 022 переводится с мок-стора на TanStack Query, ровно как 010 перевёл `/files`:**

- Новый `features/api-keys/data/api-keys.api.ts`: `injectApiKeysQuery` (`queryKey: ['api-keys']`),
  `injectIssueApiKeyMutation`, `injectReissueApiKeyMutation`, `injectRevokeApiKeyMutation` — каждая мутация
  `invalidateQueries(['api-keys'])` в `onSuccess`.
- `api-keys-page.ts`: `store` → query + мутации; `issue()/reissue()` возвращали строку синхронно — теперь
  `fullValue` приходит из ответа мутации, модалка показа открывается в `onSuccess`.
- Удаляются `data/api-keys.store.ts`, `data/api-keys.mock.ts` (мок-генератор уезжает на бэкенд целиком).
- `model/api-key.ts` → тонкий ре-экспорт типа из `packages/shared` (имена полей совпадают — `key-row`/
  `key-reveal-modal` не трогаем).
- `lastUsedAt` останется «никогда» на всех ключах до 012 — ожидаемо, в макете 022 то же самое.

### Отвергнутые варианты

| Вариант | Почему отвергнут | Когда вернёмся |
|---|---|---|
| Перевыпуск как UPDATE той же строки | Строка ключа перестаёт быть неизменной: `createdAt` либо врёт, либо прыгает; сложнее ответить «какой хеш действовал в момент T». INSERT + `revokedAt` — модель `RefreshToken` (007) | — |
| Отзыв как физический `DELETE` строки | `TECH-SPEC.md` §10 («отзыв» как атрибут) и аудит 012 (`last_used_at` отозванного) требуют, чтобы строка осталась; список фильтрует `revokedAt IS NULL` | Фоновая чистка очень старых отозванных строк, не в этом маршруте |
| argon2/bcrypt для хеша ключа | Ключ — 165 бит системной энтропии, не подбираемый пароль; `AUTH-RULES.md` §2 прямо предписывает SHA-256. Медленный хеш ударил бы по латентности каждого вызова API в 012 | — |
| Курсорная пагинация списка ключей | Предел 3 активных — весь список на одном экране; курсор был бы кодом без пользы | Если предел вырастет до сотен |
| Селектор `live`/`test` при выпуске сейчас | Поведение окружений не различается до 012 (и там не заявлено); формат ключа уже несёт признак | Появится песочница с иными лимитами |
| Отдельный `INVALID_PARAMETER` на кривой `:id` | Разный ответ на «кривой id» и «не твой ключ» — оракул существования; 010 по той же причине свёл всё в `FILE_NOT_FOUND` | — |
| `[A-Za-z0-9]` (base62) вместо `[a-z0-9]` | Больше энтропии на символ, но пример `TECH-SPEC.md` §7.1 и макет 022 — нижний регистр; 32·log2(36) ≈ 165 бит с запасом | — |

### Риски и границы транзакций

- Перевыпуск — `$transaction`: `update(revokedAt)` старого + `create` нового атомарно. Падение между шагами не
  оставляет пользователя ни без ключа при живом старом, ни с двумя живыми.
- Предел активных ключей проверяется чтением `count` вне транзакции с `create` — параллельные выпуски одного
  пользователя теоретически проведут 4-й ключ. Тот же принятый класс гонки, что квота (010) и in-memory
  лимитеры (005/007). Не 🔒-инвариант: число ключей не секрет и не даёт доступа.
- `keyHash` — `@unique`. Коллизия SHA-256 на 32 случайных символах практически невозможна; `P2002` на `create`
  не ловим специально — если случится, пусть летит в `AllExceptionsFilter` (баг ГСЧ, не пользовательский путь).
- Секрет уходит клиенту ровно в теле ответа `POST`/`reissue` и нигде не логируется: `AllExceptionsFilter` (026)
  тела не пишет, в сервисе `Logger` на выпуск не ставим.

### Мои тест-кейсы

*(владелец пишет свои прозой до кода — ниже то, что я прогоню обязательно)*

- Выпустить ключ, прочитать строку в БД напрямую: колонки с сырым значением нет, `keyHash` ≠ значению,
  `prefix` = первые 12 символов значения.
- Выпустить, скопировать значение, перевыпустить: старая строка помечена `revokedAt`, `sha256(старое)` не в
  активных; новый ключ отличается целиком.
- Отозвать ключ дважды: оба раза `204`, в БД один `revokedAt`, вторым вызовом не меняется.
- Вторым пользователем `reissue`/`DELETE` на `id` чужого ключа: `404`, чужая строка цела.
- Выпустить 3 ключа, на 4-м — `422 API_KEY_LIMIT_REACHED`; отозвать один, снова выпустить — проходит.
- Три параллельных `POST /v1/api-keys` при 2 активных: принять итог до 5 (задокументированная гонка), но не
  500 и не «минус ключ».
- Все четыре маршрута без cookie — `401`.
- Фронт: быстрый двойной клик «Выпустить» — не два ключа от одного клика; буфер обмена после копирования
  совпадает с показанным (Playwright `readText`).
