## Задача

Пользователь публичного API должен видеть свои ключи, выпускать новые, перевыпускать и отзывать скомпрометированные — без похода в бэкенд, которого ещё нет (011).

## Входит

- Экран `/api-keys` (за `authGuard`, как `/profile` и `/files`): список ключей на моке, маскированные (`ch_live_a1b2••••••••`)
- Модалка выпуска нового ключа: полный мок-ключ показывается один раз, кнопка копирования в буфер
- Перевыпуск ключа: подтверждающая модалка → новый мок-ключ, тоже показывается один раз (тот же `key-reveal`, что и при выпуске) — старый инвалидируется (`TECH-SPEC.md` §8.4)
- Отзыв ключа: подтверждающая модалка (`danger`) → ключ пропадает из списка, тост об успехе
- Пустое состояние (ключей нет)
- `last_used_at` в строке — «Никогда не использовался» на мок-данных, поле явно упомянуто в `TECH-SPEC.md` §8.4 как то, что определяет, используется ли ключ

## Не входит

| Что | Где будет |
|---|---|
| Реальные `POST /v1/api-keys`, хеширование SHA-256, `last_used_at` из реальных вызовов | 011 |
| Выбор окружения (`live`/`test`) при выпуске | Не в чек-листе 022; формат ключа сам несёт признак (`ch_live_…`/`ch_test_…`), мок всегда выпускает `live` |
| Лимиты и rate limit по ключу | 012 |
| Копирование маскированного значения в списке | Копировать нечего — маска бесполезна как значение; копирование есть только в момент показа полного ключа |

## Поведение

- Открывает `/api-keys`, список пуст → пустое состояние с кнопкой «Выпустить новый ключ».
- Список не пуст → строки: маскированный ключ (`mono`), дата выпуска, «последнее использование» или «Никогда», действия «Перевыпустить»/«Отозвать».
- Нажимает «Выпустить новый ключ» → модалка с новым мок-ключом (`ch_live_…`, случайная мок-строка), кнопкой копирования и «Готово»; после закрытия ключ появляется в списке замаскированным.
- Нажимает «Перевыпустить» на строке → подтверждающая модалка («старый ключ перестанет работать сразу») → подтверждает → та же модалка показа нового ключа, что при выпуске; маска в списке меняется на новую.
- Нажимает «Отозвать» → подтверждающая модалка (`danger`) → подтверждает → строка исчезает из списка, тост «Ключ отозван».
- Отменяет любую из модалок (кнопка, фон, `Escape`) → ничего не меняется.
- Неавторизованный на `/api-keys` → редирект на `/login`.

## Ошибочные сценарии

Сети нет — ошибок в смысле 004 тут не бывает.

| Ситуация | Что видит пользователь | Код |
|---|---|---|
| Список пуст | Пустое состояние, кнопка выпуска | — |
| `/api-keys` без сессии | Редирект на `/login` | — |

## Критерии приёмки

- [ ] `/api-keys` без сессии → редирект на `/login`
- [ ] Выпуск ключа → модалка с полным мок-значением, копирование работает, после закрытия — новая строка в списке с маской
- [ ] Перевыпуск → подтверждение → новое значение показывается один раз → маска в списке обновилась
- [ ] Отзыв → подтверждение (`danger`) → строка пропала, тост об успехе
- [ ] Пустой список → пустое состояние вместо таблицы
- [ ] Модалки закрываются по кнопке, фону и `Escape`, без побочных эффектов
- [ ] Обе темы, три языка, 320px — действия не обрезаются, маска не переполняет строку
- [ ] `pnpm typecheck` и `pnpm lint` зелёные, `any` и HEX в диффе отсутствуют

## План

### Подход

`features/api-keys/` по структуре 021: `api-keys.routes.ts`, `pages/api-keys-page/`, `components/key-row`, `data/api-keys.store.ts` (route-scoped, как `FilesStore`), `data/api-keys.mock.ts`, `model/api-key.ts`. Мок-генерация ключа — заведомо не крипто-стойкая (`Math.random()`), с явным комментарием об этом рядом (та же дисциплина, что у мок-OAuth в 019): это витрина, не секрет.

Модалка показа нового ключа (`components/key-reveal-modal`) переиспользуется и для выпуска, и для перевыпуска — различается только источник значения. Обе модалки (подтверждение + показ) идут через уже существующий `ModalService`/`shared/ui/confirm-dialog` (020/021) — новой инфраструктуры для модалок не требуется.

Копирование — `navigator.clipboard.writeText()` с `.catch(() => {})`: незачем городить обработку ошибки в мок-сценарии на локальном secure context (`localhost`).

### Отвергнутые варианты

| Вариант | Почему отвергнут | Когда вернёмся |
|---|---|---|
| Копировать маскированное значение из списка | Бесполезно — это не рабочий ключ | — |
| Выбор `live`/`test` при выпуске | Не в чек-листе, формат ключа сам несёт признак окружения | Если появится явная потребность в тестовых ключах отдельно от боевых |
| Отдельный модальный компонент для показа при выпуске и при перевыпуске | Один и тот же UX («вот значение, скопируйте, оно больше не покажется») — дублировать бессмысленно | — |
| Отозванные ключи остаются в списке с бейджем | Не в чек-листе; список короче и понятнее без архива неактивных ключей | Если понадобится аудит отозванных ключей |

### Риски и границы транзакций

БД и сеть не затрагиваются. Мок-генератор ключа — не крипто-стойкий и не должен пережить эту стадию: при подключении 011 вся генерация переезжает на бэкенд (`crypto.randomBytes` + SHA-256 хеш), фронт получает готовое значение один раз в ответе, а не создаёт его сам.

### Мои тест-кейсы

- Быстро дважды нажать «Выпустить новый ключ» подряд — не создаёт двух ключей от одного клика
- Скопировать значение, закрыть модалку, открыть «Перевыпустить» на другой строке — буфер не путает значения
- Отозвать последний ключ в списке — список корректно переходит в пустое состояние
- Тёмная тема: маска `mono` и бейдж «Никогда не использовался» читаемы
- 320px: действия «Перевыпустить»/«Отозвать» не обрезаются и не наезжают на маску (тот же класс бага, что был в 021)
