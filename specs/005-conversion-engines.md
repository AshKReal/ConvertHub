## Задача

Пользователь и клиент публичного API должны получить оставшиеся два направления конвертации из четырёх — `PNG→JPG` и `PDF→DOCX` — и увидеть в зоне загрузки настоящий прогресс отправки файла, а не таймер. Один клиент не должен быть в состоянии занять весь сервис параллельными запросами.

## Входит

- `PNG→JPG` — тот же движок, что и `JPG→PNG` (002), с параметрами качества и фона
- `PDF→DOCX` — движок по итогам эмпирической проверки (000): `pdf2docx`/`PyMuPDF`
- Предел на число одновременных конвертаций одного клиента (гость — по хешу IP, как и лимит частоты из TECH-SPEC.md §6; настоящий пользователь появится в 007)
- Подключение зоны загрузки (001/006) к реальному прогрессу отправки и реальному обрыву по кнопке отмены

## Не входит

| Что | Где будет |
|---|---|
| `DOCX→PDF` (Gotenberg) | 018, стадия 10 — единственное направление, требующее Docker |
| Семафор пула документов (8) для Gotenberg — отдельный механизм, глобальный, не per-client | 018 |
| Ограничение частоты запросов по времени (5/час гостю, 100/сутки пользователю) — другой механизм (счётчик по времени), не одновременность | 012 |
| Элементы интерфейса для выбора `quality`/`background` при `PNG→JPG` — нигде не спроектированы (`DESIGN.md` их не описывает); сервер уже принимает оба параметра с 002, здесь только доказывается, что путь целиком работает на новом направлении | Отдельная задача, если понадобится |
| Redis для состояния лимита — состояние живёт в памяти процесса, соответствует текущему нераспределённому деплою | Пересмотр при горизонтальном масштабировании, если возникнет |

## Поведение

- Когда клиент отправляет настоящий PNG с целью JPG, он получает JPG с указанными (или дефолтными) качеством и цветом фона под прозрачностью.
- Когда клиент отправляет настоящий PDF с целью DOCX, он получает DOCX-файл с максимально восстановимой структурой (не идеальное совпадение вёрстки — направление эвристическое, см. `TECH-SPEC.md` §2.2).
- Когда клиент уже держит открытыми 3 конвертации и присылает четвёртую, четвёртая отклоняется без ожидания — не встаёт в очередь.
- Когда пользователь в браузере отправляет файл, полоса прогресса отражает реально переданные байты, а переход в состояние «конвертируем» происходит по фактическому концу отправки, не по таймеру.
- Когда пользователь нажимает «отменить» во время отправки, реальный HTTP-запрос обрывается, а не просто скрывается индикатор.

## Ошибочные сценарии

| Ситуация | Что видит клиент | Код |
|---|---|---|
| У клиента уже 3 конвертации в процессе | Отказ без ожидания | `CONCURRENCY_LIMIT_EXCEEDED` |
| `PDF→DOCX`: процесс `pdf2docx` не уложился в 60 секунд | Отказ, можно повторить | `CONVERSION_TIMEOUT` |
| `PDF→DOCX`: процесс завершился с ненулевым кодом (повреждённый/нестандартный PDF) | Отказ | `CONVERSION_FAILED` |

`FILE_TOO_LARGE`/`UNSUPPORTED_FILE_TYPE`/`FILE_TYPE_MISMATCH`/`FILE_CORRUPTED` и другие коды входа — уже покрыты 002/026, работают одинаково для всех направлений, здесь не переопределяются.

## Критерии приёмки

- [ ] Настоящий PNG с прозрачностью → `JPG`, `quality=60` и `background=#000000` в форме → прозрачные пиксели становятся чёрными, файл заметно легче, чем при `quality=90`
- [ ] Настоящий PDF со сложной вёрсткой (таблицы, колонки) → `DOCX`, открывается в Word/LibreOffice, содержит настоящий текст и таблицы (не картинки/фреймы)
- [ ] Повреждённый PDF (обрезан посреди файла) → `CONVERSION_FAILED`, не зависание процесса
- [ ] 4 параллельных запроса от одного клиента (без cookie/ключа — один хеш IP) → первые 3 обрабатываются, четвёртый — немедленный `CONCURRENCY_LIMIT_EXCEEDED`, не пятая-десятая секунда ожидания
- [ ] После завершения любой из трёх — слот освобождается, следующий запрос от того же клиента снова проходит
- [ ] В зоне загрузки: реальная отправка файла размером в несколько мегабайт показывает промежуточные значения прогресса, не «0% → сразу 100%»
- [ ] В зоне загрузки: отмена во время отправки реально обрывает HTTP-запрос (проверяется по сетевой вкладке/логу сервера — соединение закрыто досрочно, не просто скрыт индикатор)
- [ ] `pnpm typecheck` и `pnpm lint` зелёные
- [ ] `any` в диффе отсутствует
- [ ] Секретов и HEX-цветов в диффе нет

## План

### Подход

**`PdfToDocxEngine` — дочерний процесс на каждый вызов**, не постоянный HTTP-сайдкар (решение владельца): `child_process.spawn('python', [scriptPath, inputPath, outputPath])`, входной PDF и выходной DOCX — временные файлы (тот же `os.tmpdir()`-паттерн, что уже есть в `convert-file.interceptor.ts`), таймаут 60 с (`TECH-SPEC.md` §6) через `setTimeout` + `child.kill()`. Скрипт `apps/api/python/pdf_to_docx.py` — тонкая обёртка над `pdf2docx.Converter`, без CLI-библиотек: два позиционных аргумента, код выхода 0/не-0. Системный `python` на `PATH` (решение владельца) — требование окружения, как Docker/Postgres уже сейчас; `apps/api/python/requirements.txt` с `pdf2docx`, установка — `docs/SETUP.md`.

**`ImageEngine` уже поддерживает `PNG→JPG`.** `supports()` и `convert()` были написаны в 002 без ограничения по направлению внутри `{JPG, PNG}` — само направление уже работает, 005 доказывает это тестом, не пишет новый код движка.

**Валидатор направлений расширяется, не создаётся заново.** `conversion-direction.validator.ts`'s `IMAGE_DIRECTIONS` — по факту уже не только про изображения (магический-байты-детект не знает о картинках как о категории), переименовывается в `SUPPORTED_DIRECTIONS` и включает все направления `packages/shared`, КРОМЕ `docx-to-pdf` (018, движка ещё нет — оставить его в списке значило бы менять код ошибки с честного `UNSUPPORTED_FILE_TYPE` на вводящий в заблуждение `CONVERSION_FAILED` от «движок не найден»).

**Лимит одновременных конвертаций — новый `ConcurrencyLimiterService`**, `Map<string, number>` в памяти модуля (решение владельца: не Redis — тот зарезервирован под 012 и пока ничем не используется), ключ — `userId ?? hashIp(req.ip)` (решение владельца: строить сейчас, не откладывать до 007, как было отложено в 002 — паттерн анонимной идентичности по хешу IP уже есть в `TECH-SPEC.md` §6 для лимита частоты, семафор параллельности использует тот же ключ). `hashIp()` — новый переиспользуемый `common/util/hash-ip.ts` (тот же хеш понадобится 012). Проверка — в начале `ConversionService.convert()`, освобождение слота — в уже существующем `finally` рядом с уборкой temp-файла. Новый код `CONCURRENCY_LIMIT_EXCEEDED` (429, retryable) — не переиспользует `RATE_LIMIT_EXCEEDED`: у них разная механика (счётчик одновременных запросов, не счётчик по времени) и разный совет клиенту («подождите секунды, пока текущий запрос завершится» vs «подождите час»); 012 создаст собственный `RATE_LIMIT_EXCEEDED`-поток независимо, путать их коды нельзя.

**Зона загрузки — реальный `HttpEventType`, не таймер.** `convert.api.ts`'s `convert()` меняет опции на `{reportProgress: true, observe: 'events', responseType: 'blob'}`, возвращает `Observable<HttpEvent<Blob>>` вместо `Observable<Blob>`. `Dropzone.start()` полностью убирает `setInterval`-имитацию (026 её оставила как временный мост, сейчас настоящий источник прогресса уже есть) — подписывается сразу, `HttpEventType.UploadProgress` двигает `progress` и переключает фазу в `converting` по факту `loaded === total`, `HttpEventType.Response` даёт готовый `Blob`. Отмена уже работала через `unsubscribe()` (026) — теперь она обрывает настоящий XHR, а не подписку на ещё не начатый запрос.

### Риски и границы транзакций

БД не участвует напрямую (история конвертаций уже пишется в 003/026 независимо от направления). Риски:

- Лимит одновременности — в памяти процесса: перезапуск сервера обнуляет счётчики (примет ещё 3 от кого угодно сразу после рестарта) — приемлемо для одного инстанса, честно фиксируется, не скрывается.
- `python`-процесс, зависший без корректного таймаута, тёк бы файловыми дескрипторами/памятью — `child.kill()` по таймеру и в `finally` временных файлов страхуют это.
- Хеш IP без соли — не проблема безопасности (не хранится, не используется как секрет, только как ключ группировки в памяти), но при желании усилить консистентность с будущим 012 стоит решить вопрос соли один раз, не по частям.

### Мои тест-кейсы

- Настоящий PNG с альфа-каналом → JPG, `quality=60`, `background=#000000` — прозрачность ушла в чёрный, файл заметно легче версии с `quality=90`
- Настоящий PDF на 30+ страниц со сложной вёрсткой → DOCX, открывается, `python-docx` находит настоящий текст и хотя бы одну таблицу
- Обрезанный посреди файла PDF → `CONVERSION_FAILED`, не зависание, процесс python не остаётся висеть
- Огромный синтетический PDF, гарантированно не укладывающийся в 60 с (или намеренно заниженный на время теста таймаут) → `CONVERSION_TIMEOUT`, дочерний процесс убит, не осиротел
- 4 параллельных запроса без идентификации (curl с `&` в фоне) — четвёртый получает `CONCURRENCY_LIMIT_EXCEEDED` мгновенно, не после ожидания
- После завершения одного из трёх — новый (четвёртый по счёту, второй по времени) запрос от того же клиента проходит
- В браузере: реальный файл несколько МБ — `network`-вкладка показывает поэтапную загрузку, полоса прогресса синхронна с ней
- В браузере: нажать «отменить» на середине отправки большого файла — запрос в `network`-вкладке помечен отменённым, а не завершается в фоне
