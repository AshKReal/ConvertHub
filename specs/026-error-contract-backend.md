## Задача

Любой отказ от `apps/api`, каким бы модулем он ни был вызван, должен приходить клиенту в одном и том же машиночитаемом формате — с кодом, человекочитаемым описанием и идентификатором запроса для переписки с поддержкой. До сих пор этот формат существовал только на клиенте (004) как заготовка, которую нечем было наполнить: сервер отдавал произвольную форму ответа в зависимости от того, какой фильтр (если вообще какой-то) перехватил исключение.

## Входит

- Единый глобальный обработчик ошибок, отдающий один и тот же формат независимо от модуля и типа исключения
- Идентификатор запроса в каждом ответе об ошибке, даже если клиент его не прислал
- Код общей непредвиденной ошибки — для случаев, не описанных ни одним доменным кодом
- Подключение готового клиентского перехватчика (004) к первому реальному сетевому запросу приложения
- Реальная (не сфабрикованная в браузере) конвертация в зоне загрузки — ровно настолько, насколько нужно увидеть настоящий код ошибки, не больше

## Не входит

| Что | Где будет |
|---|---|
| Прогресс через реальные события загрузки, переход в «конвертируем» строго по 100% отправленных байт, обрыв через настоящий HTTP | 005 |
| Проверка `Retry-After`/политики повтора на клиенте | появится вместе с 012 |
| TanStack Query, кэш и инвалидация серверных данных | 010 |
| `request_id`, генерируемый клиентом и пробрасываемый в заголовок для сквозной трассировки в логах | 014 |
| Собственные коды ошибок для auth/api-keys — регистр уже общий, добавление новых кодов по мере необходимости в 007/008/011 | 007, 008, 011 |

## Поведение

- Когда сервер отвечает любой ошибкой из своего реестра кодов, тело ответа — `application/problem+json` с полями `type`, `title`, `status`, `code`, `detail`, `instance`, `request_id`, и, если применимо, `meta`.
- Когда клиент не прислал собственный идентификатор запроса, сервер создаёт свой — идентификатор в ответе есть всегда.
- Когда исключение не относится ни к одному доменному коду (непредвиденная ошибка), клиент всё равно получает валидный `problem+json` с кодом `INTERNAL_ERROR`, а не сырой текст стека или пустое тело.
- Когда пользователь отправляет настоящий файл в зоне загрузки, он видит переведённый текст настоящей ошибки сервера (лимит размера, неподдерживаемый тип и т. д.), а не один из зашитых в компонент сценариев.

## Ошибочные сценарии

| Ситуация | Что видит клиент | Код |
|---|---|---|
| Исключение не соответствует ни одному коду из реестра (непредвиденный сбой) | `500`, тело `problem+json` с этим кодом | `INTERNAL_ERROR` |

Остальные коды уже описаны в 002/003/004 — 026 не создаёт новых доменных кодов, только общий фолбэк и оболочку формата.

## Критерии приёмки

- [ ] `POST /v1/convert` с файлом на 1 байт больше лимита → `application/problem+json`, поля `type`/`title`/`status`/`code`/`detail`/`instance`/`request_id` все присутствуют, `code === 'FILE_TOO_LARGE'`, `detail` содержит оба размера в байтах
- [ ] Тот же запрос без заголовка с id — `request_id` в ответе всё равно есть и не пустой
- [ ] Искусственно брошенное непредвиденное исключение → `500`, `code === 'INTERNAL_ERROR'`, форма ответа та же, что у остальных ошибок
- [ ] `GET /v1/files/{несуществующий id}/download` (003, без собственного `@UseFilters`) → тот же формат `problem+json`, `code === 'FILE_NOT_FOUND'` — подтверждает, что фильтр действительно глобальный, а не только для `/v1/convert`
- [ ] В зоне загрузки (`/convert/:direction`): настоящий файл больше лимита → на экране переведённый текст `FILE_TOO_LARGE` с реальными числами из ответа сервера, а не заглушка `MOCK_FORCE_CONVERSION_ERROR`
- [ ] Настоящий валидный файл в зоне загрузки → настоящая конвертация, скачивается реальный результат, а не копия исходного файла
- [ ] `pnpm typecheck` и `pnpm lint` зелёные
- [ ] `any` в диффе отсутствует
- [ ] Секретов и HEX-цветов в диффе нет

## План

### Подход

`AllExceptionsFilter` — единственное место, которое сериализует исключение в `problem+json`; регистрируется глобально (`APP_FILTER`). Существующие контроллерные фильтры (`MulterExceptionFilter`, `ConversionFailureFilter` из 003) сохраняют свою работу (уборка temp-файла, перевод `PayloadTooLargeException`, запись истории конвертации), но больше не рендерят ответ сами — на последнем шаге вызывают `AllExceptionsFilter.catch()` тем же способом, каким `ConversionFailureFilter` уже вызывает `MulterExceptionFilter` (см. её докблок, спека 003): напрямую как метод обычного инжектируемого провайдера, не как второй зарегистрированный Nest-фильтр (два независимых `@Catch()` подряд не работают одновременно). Это меняет `multer-exception.filter.ts` — уже написанный и протестированный в 002 файл, но иначе он остался бы островом со своим форматом ответа.

`AppException` — уже единственный тип, которым бросаются доменные ошибки (002/003), фильтр читает `code`/`meta` из его тела. Всё, что не `AppException`, но всё же `HttpException` (например, `NotFoundException` на несуществующий маршрут — за пределами задокументированного контракта, но реально происходит на любой опечатке в URL) — сохраняет свой настоящий HTTP-статус, получает код `INTERNAL_ERROR`. Всё остальное (непредвиденное исключение, не `HttpException` вообще) — `500` и тот же код, с логированием (`Logger.error`) — доменные ошибки (`AppException`) не логируются как ошибки: это ожидаемые исходы, не баги.

Текст `detail` — на английском, для интеграторов API, не для конечного пользователя (тот получает свой переведённый текст на клиенте через уже готовый 004). Явная карта код → функция от `meta`, живёт в `common/` (`apps/api`-специфична, не нужна фронту — `packages/shared` не годится). `title` не хранится по коду отдельно — вычисляется из имени кода механической заменой (`FILE_TOO_LARGE` → `File too large`), у примера в TECH-SPEC.md §7.5 то же самое правило.

`request_id`: заголовок `X-Request-Id` от клиента, если есть, иначе `req_${ulid()}` — выбор заголовка не описан нигде в документах (клиентская генерация — 014, ещё не реализована), поэтому это первое решение по имени, а не подтверждение уже существующего.

На клиенте: `provideHttpClient(withInterceptors([errorInterceptor]))` — первый реальный сетевой вызов во всём фронтенде, поэтому и первая регистрация `HttpClient` в `app.config.ts`. Реальная отправка — новый `features/convert/data/convert.api.ts` (правило `frontend.md`: компонент не вызывает `HttpClient` напрямую), обычная функция с `inject(HttpClient)` внутри контекста инъекции, без TanStack Query — она не даёт здесь ничего (ни кэша, ни инвалидации для одноразового POST с бинарным ответом), понадобится в 010 для настоящего `GET /v1/files`. `Dropzone` заменяет таймер-фейк исхода конвертации (`MOCK_FORCE_CONVERSION_ERROR`, повторная выдача исходных байт под видом результата) на реальный вызов в момент, когда таймер прогресса и так уже доходит до состояния `converting` — сам прогресс остаётся визуальной имитацией (реальные события загрузки — 005), меняется только источник итога: настоящий ответ сервера вместо зашитого сценария.

**Настоящая техническая находка, не видна по документации, только по поведению `HttpClient`:** запрос с `responseType: 'blob'` (нужен, чтобы получить бинарный результат конвертации) заставляет Angular трактовать *любое* тело ответа как `Blob` — включая тело ошибки. `HttpErrorResponse.error` в этом случае не разобранный JSON, а сырой `Blob`, и существующий `errorInterceptor` (004) молча не находит в нём `code`, откатываясь на `CONVERSION_FAILED` для абсолютно любой реальной ошибки. Без исправления критерий приёмки «показывает настоящие коды ошибок» не выполняется никогда, вне зависимости от того, что делает сервер. `errorInterceptor` дополняется веткой: `error.error instanceof Blob` → прочитать текст, разобрать JSON, и только потом строить `AppError` — асинхронно, через `from()`/`switchMap`, остальной путь (не-Blob тело) не меняется.

### Отвергнутые варианты

| Вариант | Почему отвергнут | Когда вернёмся |
|---|---|---|
| Хранить `detail`-тексты в `packages/shared` рядом с кодами | Пакет не должен тянуть предположения о том, кто их использует (сервер, английский, для интеграторов) — фронт уже переводит свои тексты независимо (004); дублирование двух наборов строк по одному ключу разойдётся | — |
| `MulterExceptionFilter`/`ConversionFailureFilter` остаются с `super.catch()`, `AllExceptionsFilter` — только для новых модулей | Тогда `/v1/convert` — единственный маршрут — не получил бы единый формат, а именно на нём проверяется контракт | — |
| `title` — по явной карте, как коды ошибок на клиенте | Текст title не показывается пользователю (это делает 004 через свой словарь), значение не критично — механическое правило точно покрывает уже задокументированный пример без ручного набора 17 строк | Если `title` когда-нибудь станет пользователь-видимым |
| TanStack Query для `POST /v1/convert` уже в 026 | Мутация без кэша/инвалидации не получает ничего от библиотеки; откладывает первую установку зависимости до реальной необходимости (010, список файлов) | 010 |
| `CONVERSION_FAILED` как фолбэк для непредвиденных ошибок вместо нового кода | Текст код-специфичен («Conversion failed unexpectedly»); будущие auth/api-keys модули будут бросать непредвиденные ошибки, не имеющие отношения к конвертации | — |

### Риски и границы транзакций

БД не участвует. Риск — регресс уже протестированного в 002 поведения `MulterExceptionFilter` (лимит размера файла, уборка temp-папки): меняется способ рендера ответа, логика перед ним — нет; проверяется тем же ручным тестом на 11 МБ файле, что и в 002.

### Мои тест-кейсы

- Файл на 1 байт больше лимита — тело `problem+json`, все семь полей на месте, числа в `detail` совпадают с `meta`
- Тот же запрос с собственным `X-Request-Id: test-123` — сервер возвращает именно его, не генерирует новый
- `GET /v1/files/{несуществующий}/download` — тот же формат, `code: FILE_NOT_FOUND`, без явного `@UseFilters` на контроллере (доказывает, что фильтр глобальный)
- Искусственный `throw new Error('boom')` внутри временно добавленного тестового маршрута — `500`, `code: INTERNAL_ERROR`, в логе сервера есть стек
- Реальный файл больше лимита через зону загрузки в браузере — баннер/тост показывает текст с настоящими числами, не текст `MOCK_FORCE_CONVERSION_ERROR`
- Реальный валидный JPG через зону загрузки — скачанный файл действительно PNG (не переименованная копия исходного JPG)
- Отключить сеть до момента конвертации (после выбора файла) — ошибка показывается, а не зависшее состояние `converting` навсегда
