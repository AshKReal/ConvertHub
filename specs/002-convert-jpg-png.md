## Задача

Пользователь или клиент публичного API отправляет изображение в одном из двух поддерживаемых форматов и получает его же в другом. Сервис не имеет права доверять заявленному типу файла — определяет его сам по содержимому, отклоняет файлы, способные исчерпать память ещё до попытки их разобрать, и гарантированно не оставляет своих временных следов на диске после ответа, каким бы он ни был.

## Входит

- Приём файла из тела запроса потоком во временное место на диске, не целиком в память
- Определение реального типа файла по содержимому, независимо от расширения и заявленного типа
- Отклонение файла, чьи заявленные размеры способны исчерпать память при разборе, до попытки разобрать содержимое полностью
- Само преобразование между двумя форматами с учётом необязательных параметров качества и цвета фона
- Гарантированная уборка временных файлов после каждого запроса независимо от исхода

## Не входит

| Что | Где будет |
|---|---|
| Сохранение результата в постоянное хранилище, квота | 003 |
| Ограничение числа одновременных конвертаций на пользователя | 005 |
| Аутентификация запроса, ограничение частоты запросов | 007, 012 |
| Полный формат ответа об ошибке целиком (машиночитаемый адрес проблемы, заголовок) | 026 |
| Направления, отличные от двух форматов изображений | 005, 018 |

## Поведение

- Когда клиент отправляет настоящий файл первого формата с целью — второй, он получает файл второго формата.
- Когда заявленное расширение или тип не совпадают с реальным содержимым файла, запрос отклоняется без попытки преобразования.
- Когда содержимое заявляет о размере, способном исчерпать память при разборе, запрос отклоняется прежде, чем это содержимое будет разобрано.
- Когда файл повреждён и не читается как заявленный формат, запрос отклоняется с этим объяснением, а не общей ошибкой.
- Когда соединение обрывается посреди отправки файла, сервер не оставляет частично принятый файл на диске.

## Ошибочные сценарии

| Ситуация | Что видит клиент | Код |
|---|---|---|
| Файл больше предельного размера | Отказ до начала обработки | `FILE_TOO_LARGE` |
| Реальный тип содержимого не входит в поддерживаемые | Отказ | `UNSUPPORTED_FILE_TYPE` |
| Реальный тип — из поддерживаемых, но не тот, что подразумевает цель | Отказ | `FILE_TYPE_MISMATCH` |
| Заявленное разрешение превышает безопасный предел | Отказ до разбора содержимого | `IMAGE_TOO_LARGE` |
| Файл не читается как заявленный формат | Отказ | `FILE_CORRUPTED` |
| Некорректные параметры запроса | Отказ | `INVALID_PARAMETER` |
| Непредвиденный сбой при преобразовании | Отказ, можно повторить | `CONVERSION_FAILED` |

## Критерии приёмки

- [x] Настоящий JPG, цель — второй формат → 200, тело — валидный файл второго формата
- [x] Настоящий файл с прозрачностью, цель — формат без альфа-канала, указан цвет фона → прозрачные пиксели становятся этим цветом
- [x] Файл одного формата, переименованный в расширение другого, с целью, совпадающей с расширением → отказ `FILE_TYPE_MISMATCH`
- [x] Файл постороннего формата, переименованный в поддерживаемое расширение → отказ `UNSUPPORTED_FILE_TYPE`
- [x] Файл на 1 байт больше предельного размера → отказ `FILE_TOO_LARGE`, временных файлов на диске не осталось
- [x] Файл с заведомо огромным заявленным разрешением → отказ `IMAGE_TOO_LARGE`, ответ быстрый, полный разбор содержимого не происходит
- [x] Обрезанный/повреждённый файл → отказ `FILE_CORRUPTED`
- [x] `pnpm --filter api typecheck` и `pnpm --filter api lint` зелёные
- [x] `any` в диффе отсутствует
- [x] Секретов в диффе нет (цвет фона по умолчанию — обычное значение параметра, не токен дизайна и не HEX в разметке — правило DESIGN.md к бэкенду не относится)

## План

### Подход

Первый настоящий модуль `apps/api` — структура по `ARCHITECTURE.md` §4.1: `modules/conversion/` с `engines/` (движки, только этот модуль) и `validators/` (проверки недоверенного файла, 🔒). Интерфейс `ConversionEngine` фиксирован заранее (не меняется в 018, когда появится HTTP-движок Gotenberg) — сигнатура `convert(input: Buffer, opts): Promise<Buffer>`, движок для sharp — первая и пока единственная реализация.

`AllExceptionsFilter` (026) и `ZodValidationPipe` (правило `backend.md`) физически не существуют. `ZodValidationPipe` — пишем минимальный сейчас в `common/pipes/`, это общий переиспользуемый паттерн, не только для 002. Ошибки — свой `AppException extends HttpException` с телом `{code, meta?}`: этого достаточно клиентскому `errorInterceptor` уже сейчас (он читает `code`/`meta`, `request_id` у него и так опционален), полный RFC 9457 — задача 026.

Определение типа — `file-type` (magic bytes, не по расширению/`Content-Type`). Приём файла — `multer`/`FileInterceptor` (уже транзитивная зависимость `@nestjs/platform-express`) с `diskStorage`, поток сразу в `os.tmpdir()/convert-hub/<uuid>/<uuid>`, без расширения и без имени от клиента в пути. Пиксельный лимit — `sharp(path).metadata()`, читает только заголовок, не декодирует пиксели.

Семафор одновременных конвертаций (упомянут в `tasks.md` для 005, «3 на пользователя») в 002 не добавляется: identity ещё нет (007 не существует), глобальный счётчик без пользователя либо душит всех одинаково, либо бесполезен — и станет мёртвым кодом при появлении per-user-версии в 005. Существующие пределы (10 МБ на файл, 50 Мп до декодирования) уже ограничивают худший случай на один запрос; открытый риск (неограниченное число параллельных анонимных запросов) — известный пробел до 005/012, не решается здесь.

### Найдено ручной проверкой, не было видно по чтению документации

- `@nestjs/platform-express`'s `FileInterceptor` сам перехватывает сырой `multer.MulterError` и превращает `LIMIT_FILE_SIZE` в свой `PayloadTooLargeException` (`multer.utils.js`, `transformException`) прежде, чем ошибка доходит до `MulterExceptionFilter` — сырой `MulterError` туда не долетает никогда. Фильтр изначально проверял `instanceof MulterError`, не срабатывал, и клиенту уходил дефолтный формат Nest (`{message, error, statusCode}`), не контрактный `{code, meta}`. Исправлено: фильтр проверяет `instanceof PayloadTooLargeException`.
- `sharp(path).metadata()` без опций сама отказывает уже на заголовке, если заявленное разрешение превышает **собственный** лимит sharp по умолчанию (~268 Мп) — на файле 20000×20000 (400 Мп) это происходило раньше, чем наша проверка успевала отличить decompression bomb (`IMAGE_TOO_LARGE`, с числами) от повреждённого файла: `metadata()` бросала исключение, и оно попадало в тот же `catch`, что и настоящая порча (`FILE_CORRUPTED`). Исправлено: `limitInputPixels: false` именно на этом чтении заголовка — `metadata()` не декодирует пиксели, это безопасно; решающий лимит — наша собственная проверка сразу после.
- `@Res()`-обработчик получает от Nest статус по умолчанию для метода (`POST` → 201), даже когда ответ формируется вручную. Успешная конвертация ничего не «создаёт» — добавлен явный `@HttpCode(200)`.

### Риски и границы транзакций

БД не участвует, транзакций нет. Риски:

- Ревью-скоуп: автоматически критичной зоной по `.claude/rules/critical-zones.md` считается только `validators/**`, но по факту недоверенные байты и пути проходят и через контроллер, сервис, движок, приёмщик файла — построчная проверка нужна всем новым файлам этой спеки, не только `validators/`.
- Значения по умолчанию для необязательных параметров (цвет фона, качество) нигде не зафиксированы в ТЗ/TECH-SPEC — предложены как отраслевой стандарт, не описаны заранее; при несогласии владельца меняются одной строкой.
- До 005/012 нет предела на число одновременных запросов от одного анонимного клиента — известный, принятый пробел, не решается здесь.
- Требуется первая установка зависимостей в `apps/api` (`sharp`, `file-type`, `multer`) — возможна необходимость правки корневого `pnpm.onlyBuiltDependencies`, выясняется по факту установки, не предполагается заранее.

### Мои тест-кейсы

- Настоящий файл первого формата → второй, без необязательных параметров
- Настоящий файл с прозрачностью → формат без альфы, с указанным цветом фона и качеством — прозрачность корректно ушла в указанный цвет
- Файл первого формата, переименован в расширение второго, цель совпадает с расширением — отказ по несовпадению
- Файл постороннего формата, переименован в поддерживаемое расширение — отказ по неподдерживаемому типу
- Файл ровно на предельном размере — принят; на байт больше — отказ, временных файлов не осталось
- Файл с заведомо огромным заявленным разрешением, но крошечными реальными данными — быстрый отказ, без попытки полного разбора
- Файл, обрезанный сразу после заголовка, и файл, обрезанный в данных после валидного заголовка — оба отказ по повреждению, из разных точек кода
- Обрыв соединения на середине отправки валидного файла — сервер не падает, временных следов не остаётся
