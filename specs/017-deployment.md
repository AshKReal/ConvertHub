## Задача

Всё написано и упаковано, но сервиса не существует: образ никуда не выкатывается, `apiUrl` фронта пуст,
конфигурации площадок в репозитории нет. Стадия 11 поднимает ConvertHub на Railway (бэкенд, Gotenberg,
managed Postgres/Redis), Vercel (статика) и Cloudflare R2 (файлы) и доводит репозиторий до состояния, в
котором деплой воспроизводим по документу, а не по памяти.

## Входит

- `vercel.json` — настройки сборки, обратный прокси `/v1/*` на Railway, SPA-fallback, запрет кеширования API.
- `environment.prod.ts` — зафиксировать пустой `apiUrl` как рабочее значение и объяснить почему.
- Исправление проверки происхождения запроса в интерцепторах фронта, которую ломает пустой `apiUrl`.
- `enableShutdownHooks()` — иначе `SIGTERM` от площадки не закрывает соединения.
- `start:prod` с верным путём точки входа (`INFRA-06`).
- `docs/DEPLOYMENT.md` под фактическую топологию.
- README для внешнего читателя: корневой + замена болванок в `apps/api` и `apps/web` (`DOC-06`).

## Не входит

- Публикация образа в registry (GHCR) — Railway собирает из репозитория сам.
- Автодеплой из CI: пуш в `main` деплоем не является, выкатывает площадка по своему хуку.
- Несколько инстансов `api` и вынос миграций в отдельный шаг — при одном инстансе миграции в entrypoint
  безопасны, при нескольких пойдут параллельно.
- Helmet/HSTS/CSP (`TECH-SPEC.md` §12) — новая зависимость и смена поведения на всех маршрутах, не место в
  деплойном изменении. Заведено находкой `INFRA-10`.
- Закрытие 13 открытых 🟠 из `REVIEW-FINDINGS.md` — решение владельца «деплоим как есть».

## Поведение

Браузер общается только с Vercel. Статика отдаётся оттуда, `/v1/*` проксируется на Railway. Фронт и API — один
origin, поэтому refresh-cookie остаётся `SameSite=Lax` и first-party. Контейнер `api` при старте применяет
миграции и поднимается; при остановке получает `SIGTERM` и закрывает Prisma и Redis.

## Ошибочные сценарии

| Что | Как проявляется |
|---|---|
| Хост Railway не вписан в `vercel.json` | все вызовы API возвращают HTML вместо JSON |
| Правило `/v1/:path*` стоит после SPA-fallback | то же самое: fallback перехватывает первым |
| Нет SPA-fallback | 404 на `/login`, `/files`, `/reset-password/<токен>` из письма |
| `GOOGLE_REDIRECT_URI` на домене Railway | cookie `oauth_state` не доезжает, вход через Google даёт «попробуйте ещё раз» |
| `CORS_ORIGIN` на домене Railway | ссылка из письма сброса ведёт на голый API |
| Плейсхолдер в секрете | контейнер не стартует — так задумано (`INFRA-01`) |
| Тело больше потолка прокси | большой файл падает при работающем маленьком (§9 `DEPLOYMENT.md`) |

## Критерии приёмки

1. `https://<vercel>/v1/openapi.json` отдаёт JSON — прокси работает.
2. Регистрация → вход → **F5**: сессия пережила перезагрузку. Главный критерий: ради этого выбран прокси.
3. `JPG → PNG` файлом ~9 МБ проходит целиком, файл скачивается и это действительно PNG.
4. `DOCX → PDF` и `PDF → DOCX` работают — Gotenberg по приватной сети и Python в образе.
5. Прямая ссылка `/reset-password/<что угодно>` в новой вкладке открывает приложение, а не 404.
6. Вход через Google — полный цикл до возврата на фронт.
7. Письмо сброса пароля приходит, ссылка ведёт на домен Vercel.
8. `/health` и `/ready` напрямую к Railway — `ok`; `/metrics` без токена — `401`.
9. Gotenberg не имеет публичного домена.

## План

### Решения владельца (2026-09-04)

- Домены — дефолтные `*.vercel.app` / `*.up.railway.app`, свой домен не заводится.
- Из-за этого refresh-cookie решается **обратным прокси**, а не правкой cookie: см. «Отвергнутые варианты».
- Деплоим как есть: 13 открытых 🟠 не блокируют.
- Ветка от `main`, PR в `main` (правило про `backend` в `CLAUDE.md` устарело — ветка мертва).

### Подход

Прокси на Vercel вместо второго домена. Всё остальное — следствия: пустой `apiUrl` становится рабочим
значением, а не заглушкой; проверка «наш ли это запрос» перестаёт опираться на origin и переезжает на префикс
пути; `GOOGLE_REDIRECT_URI` и `CORS_ORIGIN` указывают на Vercel, а не на API.

### Отвергнутые варианты

**Купить домен** (`example.com` + `api.example.com`). Работает, ничего в коде не меняет, `DEPLOYMENT.md` был
написан именно под это. Отвергнут владельцем: заводить домен под учебный проект не хочется.

**`SameSite=None; Secure`.** Правка в 🔒-зоне `modules/auth/**`: два `res.cookie` и два `clearCookie` —
последним тоже пришлось бы носить новые атрибуты, иначе logout перестал бы гасить cookie, и это заметили бы
не сразу. Плюс отступление от `AUTH-RULES.md` §35 с записью в `docs/SECURITY.md` и построчной приёмкой.
Отвергнут не поэтому, а потому что **не работает**: такая cookie сторонняя, Safari блокирует сторонние cookie
по умолчанию (ITP). Платить правкой в самой чувствительной зоне за решение, ломающееся у части пользователей,
смысла нет.

### Риски и границы

**Главный риск — потолок прокси.** Заливка до 10 МБ и конвертация до 60 с идут через Vercel. Лимитов тела и
таймаута для внешних `rewrites` документация не публикует, а serverless-функции той же площадки имеют потолок
4.5 МБ — именно из-за него `TECH-SPEC.md` §13 отклонил serverless для бэкенда. Проверяется только на живом
деплое, критериями 3 и 4. Откат — `DEPLOYMENT.md` §9: домен либо `SameSite=None`; и то и другое требует
вернуть домен API в `environment.prod.ts` и пересобрать фронт.

Миграции в entrypoint безопасны только при одном инстансе. Направление `DOCX→PDF` рантайм-переключателя не
имеет: живо с момента деплоя.

### Мои тест-кейсы

Автотестами покрывается ровно одно — ловушка пустого `apiUrl` (`api-url.spec.ts`): относительные пути API
признаются своими, посторонний запрос — нет, и то же самое на dev-конфигурации, где баг не воспроизводится.
Без параметризации ядра тест был бы невозможен: Angular-раннер запрещает `vi.mock` для относительных импортов.

Остальное — конфигурация площадок, автотестом не проверяется; её проверяют критерии приёмки руками.
