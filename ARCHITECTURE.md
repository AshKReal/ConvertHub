## 1.1 Поэтапное подключение

Схема выше — цель. Компоненты подключаются не одновременно: каждый появляется в тот момент, когда без него нельзя двигаться дальше.

**Весь фронтенд (стадии 0–3) строится без Docker вообще** — экраны на локальных моках, без сети (`TECH-SPEC.md` §14). **Postgres и Redis — `docker compose` со стадии 4**, начала бэкенд-фазы, а не managed-инстанс: в корне репозитория `docker-compose.yml` поднимает ровно эти два сервиса (healthcheck обязателен на оба — без него `depends_on` не дождётся готовности). Managed остаётся только для продакшена (Railway, раздел 10) — локально ни то ни другое руками не разворачивается. Остальное — объектное хранилище, Gotenberg, `Dockerfile` приложения, CI — по-прежнему подключается позже, когда без него нельзя двигаться дальше.

Полная таблица «чем компонент заменяется до своей стадии» и разбивка по стадиям 0–11 — TECH-SPEC.md §3.2 и §14. Не дублируется здесь: копия расходится с оригиналом за пару недель, и вы этого не заметите, потому что читать будете тот документ, который ближе.

Ключевое свойство такого порядка: **ни один переход не требует менять прикладной код.** Storage и ConversionEngine — интерфейсы (раздел 4.2), Gotenberg — HTTP-адрес. Если при переходе пришлось править `conversion.service.ts` — значит абстракция протекла, и это сигнал, а не мелочь.

Качество конвертации документов LibreOffice проверяется первым в бэкенд-фазе, стадия 4, без Docker: `soffice --headless --convert-to pdf` на два-три десятка реальных файлов. Gotenberg (стадия 10) именно это оборачивает по HTTP.

## 2. Три границы

Всё остальное — детали реализации. Эти три нарушать нельзя.

### Граница 1. API не хранит файлы у себя

Ни на диске, ни в базе. В таблице `files` лежит `storage_key`, байты — в объектном хранилище.

Нарушение ломает горизонтальное масштабирование: инстанс A сохранил файл на свой диск, запрос на скачивание пришёл на инстанс B, файла нет. Плюс данные исчезают при пересоздании контейнера.

### Граница 2. Конвертер не имеет доступа к базе и к сети

Gotenberg получает файл по HTTP, возвращает файл. Он не знает про пользователей, квоты и ключи. Контейнер запускается с `network_mode: none` относительно внешнего мира, `read_only`, `tmpfs` на `/tmp`, `cap_drop: ALL` и лимитом памяти.

Смысл: конвертер разбирает недоверенный ввод в парсерах, которые исторически являются источником RCE. При компрометации злоумышленник оказывается в контейнере без состояния, без сети и без данных.

### Граница 3. Скачивание идёт мимо API

`GET /v1/files/{id}/download` отвечает `302` с подписанной ссылкой на объектное хранилище (TTL 15 минут). Байты летят напрямую от хранилища к клиенту.

Проксирование через Node заняло бы event loop и память на всё время скачивания и не масштабировалось бы.

Одна Zod-схема даёт три вещи: валидацию на бэкенде через pipe, валидацию формы на фронте, TypeScript-тип для обеих сторон.

```ts
export const convertSchema = z.object({
  target:     z.enum(['png', 'jpg', 'pdf']),
  save:       z.boolean().optional(),
  quality:    z.number().int().min(60).max(100).optional(),
  background: z.string().regex(/^#[0-9A-Fa-f]{6}$/).optional(),
  dpi:        z.union([z.literal(72), z.literal(150), z.literal(300)]).optional(),
});
export type ConvertInput = z.infer<typeof convertSchema>;
```

Меняете диапазон качества — правка в одном файле, и фронт перестаёт компилироваться там, где захардкожено старое значение. Без общего пакета фронт и бэк валидируют по разным правилам примерно через месяц.

## 4. Backend

### 4.1 Структура

```
apps/api/src/
├── main.ts
├── app.module.ts
├── config/                 env через Zod, типизированный доступ
├── common/
│   ├── filters/            AllExceptionsFilter → problem+json
│   ├── guards/             JwtGuard, ApiKeyGuard, RateLimitGuard
│   ├── interceptors/       request-id, логирование, тайминги
│   └── pipes/              ZodValidationPipe
├── prisma/
│   ├── schema.prisma
│   └── migrations/
├── modules/
│   ├── auth/               регистрация, вход, OAuth, восстановление
│   ├── users/              профиль, настройки, удаление
│   ├── api-keys/           выпуск, хеширование, проверка
│   ├── conversion/
│   │   ├── conversion.service.ts
│   │   ├── engines/
│   │   │   ├── engine.interface.ts
│   │   │   ├── image.engine.ts        sharp
│   │   │   ├── document.engine.ts     Gotenberg
│   │   │   └── pdf.engine.ts
│   │   └── validators/                magic bytes, бомбы, лимиты
│   ├── files/              список, скачивание, удаление, квота
│   └── storage/
│       ├── storage.interface.ts
│       └── s3.storage.ts
└── health/
```

**Модули снаружи, слои внутри.** Верхний уровень делится по фичам, а не по слоям: при структуре `controllers/ services/ models/` на весь проект понимание одной фичи требует открыть три папки, а связность внутри каждой нулевая. Внутри модуля деление на слои, наоборот, нужно.

Состав модуля — три обязательных файла, остальное по мере появления содержимого:

```
modules/conversion/
├── conversion.module.ts          обязателен
├── conversion.controller.ts      обязателен, если есть HTTP
├── conversion.service.ts         обязателен
├── dto/                          типы запроса и ответа
├── models/                       доменные типы (см. ниже)
├── engines/                      только у этого модуля
└── validators/                   только у этого модуля
```

Модуль заводится, когда у него есть свой маршрут или своя сущность в БД. «На всякий случай» — не заводится.

**Ответственность слоёв.**

| Слой | Делает | Не делает |
|---|---|---|
| Controller | разбирает запрос, вызывает сервис, формирует ответ и статус | логика, обращения к Prisma |
| Service | логика, Prisma, транзакции, вызовы других сервисов | не знает про `Request`, `Response`, заголовки |
| Validator / Engine | одна проверка или одно преобразование | оркестрация |

Проверка, что контроллер чистый: можно ли вызвать ту же операцию из CLI-скрипта, не тронув сервис? Проверка, что сервис чистый: встречается ли в нём `@Res()` или `res.status(...)`? Если да — HTTP протёк в логику, и на этом сломается публичный API, которому нужен другой формат ответа.

**Репозиториев поверх Prisma нет.** Prisma Client уже репозиторий: типизированный, с транзакциями, генерируемый из схемы. Обёртка над ним переименовывает методы и при этом теряет частичные выборки, `include` и типизацию результата.

**Три иерархии типов — главная ловушка.** Самая частая ошибка в связке Nest + Prisma + Zod: для одной сущности заводятся класс `FileDto`, тип `File` из `@prisma/client` и интерфейс `FileModel`. Через месяц они расходятся, и появляются мапперы между тремя почти одинаковыми структурами.

| Что это | Где живёт | Как получить тип |
|---|---|---|
| Форма запроса или ответа API | `packages/shared/src/schemas/` | `z.infer<typeof convertSchema>` |
| Строка таблицы | `schema.prisma` | `import { File } from '@prisma/client'` |
| Результат операции, опции движка | `modules/<name>/models/` | обычный `type` |

Следствия: DTO руками не пишутся и `class-validator` не подключается — он дублировал бы Zod-схему; Prisma-объект не отдаётся наружу как ответ API (в строке есть `storage_key` и служебные поля); если `models/` пуста — папку не создавать.

**Границы модулей.** Модуль экспортирует сервис только если его вызывает другой модуль. Прямой импорт файла из чужого модуля минуя `imports` даст либо «provider not found» на старте, либо, что хуже, второй экземпляр сервиса со своим состоянием. Двусторонняя зависимость модулей — сигнал неверной границы; `forwardRef` откладывает проблему, а не решает.

**`common/` — это не `packages/shared`.** В `common/` серверная инфраструктура, её видит только бэкенд. В `shared` то, что видят обе стороны. Если тип нужен фронту, он не может лежать в `common/`; если код тянет `@nestjs/*`, он не может лежать в `shared`.

**Именование:** файлы `kebab-case` с суффиксом роли (`magic-bytes.validator.ts`), классы `PascalCase`. Суффикс нужен: десять вкладок `index.ts` в редакторе неразличимы.

### 4.2 Абстракций ровно две

```ts
export interface ConversionEngine {
  supports(from: string, to: string): boolean;
  convert(input: Buffer, opts: ConvertOptions): Promise<Buffer>;
}

export interface Storage {
  put(key: string, body: Buffer, mime: string): Promise<void>;
  getSignedUrl(key: string, ttlSeconds: number): Promise<string>;
  delete(key: string): Promise<void>;
  list(prefix: string): AsyncIterable<string>;
}
```

Обе оправданы: движки будут меняться и в тестах нужен фейк; хранилище — MinIO локально и R2 в эксплуатации.

Больше ничего абстрагировать не надо. Репозитории поверх Prisma, интерфейсы для сервисов «на будущее», фабрики ради фабрик — это слои без содержания.

### 4.3 Env валидируется при старте

## 5. Поток конвертации

```
 1. Клиент: валидация размера и расширения через File API
 2. POST /v1/convert (multipart)
 3. Guard: JwtGuard либо ApiKeyGuard
 4. Guard: RateLimitGuard — token bucket в Redis
 5. Pipe:  ZodValidationPipe на поля формы
 6. Приём файла потоком во временный каталог
 7. Определение реального типа по magic bytes
 8. Проверка допустимости направления
 9. Валидаторы: бомбы, страницы, разрешение
10. Семафор: занять слот в пуле (8 для документов)
11. ConversionEngine.convert()
      ├── jpg/png → sharp, в памяти
      ├── docx    → HTTP POST в Gotenberg
      └── pdf     → рендер страниц
12. Если save=true и квота позволяет:
      ├── Storage.put()
      └── ТРАНЗАКЦИЯ: insert files + update storage_used_bytes
13. Insert в conversions (статус, длительность, код ошибки)
14. finally: удалить временные файлы, освободить слот
15. Ответ: бинарный файл либо JSON
```

Шаг 12 — единственная транзакция. Запись в `files` и увеличение счётчика квоты атомарны, иначе счётчик разъезжается с реальностью.

Шаг 14 в `finally`: временные файлы удаляются и при исключении. Иначе диск заполняется мусором за сутки.

**Валидация на клиенте не отменяет серверную.** Клиентская экономит пользователю трафик, серверная защищает систему. Обойти клиентскую можно за десять секунд в DevTools.

## 6. Frontend

### 6.1 Слои

```
src/app/
├── core/          инфраструктура, один экземпляр на приложение
│   ├── api/       типизированный ApiClient
│   ├── interceptors/  auth, ошибки, request-id
│   ├── guards/    authGuard, guestGuard
│   └── services/  AuthService, ToastService
├── shared/        переиспользуемое без домена
│   ├── ui/        компоненты Spartan — ваш код
│   └── pipes/     formatBytes, relativeDate
└── features/      по папке на раздел, ленивая загрузка
    ├── home/ convert/ files/ profile/ auth/ api-docs/
```

**Стрелки зависимостей идут только вниз.** `features/convert` не импортирует из `features/files`. Общий код переезжает в `shared`. Нарушение ломает разбиение на ленивые чанки: всё склеивается в один бандл, и это видно по размеру сборки.

```
features → shared    можно        shared → core       нельзя
features → core      можно        core → features     нельзя
                                  features → features нельзя
```

**Устройство одной фичи:**

```
features/convert/
├── convert.routes.ts
├── pages/convert-page/        экраны, привязанные к маршруту
├── components/dropzone/       про роутинг не знают, данные через входы
├── data/
│   ├── convert.api.ts         единственное место с HttpClient
│   └── convert.store.ts       состояние фичи на сигналах
└── model/dropzone-state.ts    типы фичи, не дублируют packages/shared
```

**Компоненты не вызывают `HttpClient` напрямую** — только через `data/*.api.ts`. Иначе один эндпоинт вызывается из трёх мест с тремя вариантами обработки ошибок, и это выясняется при первом изменении контракта.

**Критерий для `shared/ui`:** компонент можно скопировать в другой проект, и он скомпилируется. Не инжектит `HttpClient`, не импортирует доменные типы. `StatusBadge`, принимающий `'completed' | 'failed'`, — общий; принимающий объект `Conversion` — доменный, его место в фиче.

**Состояние.** Локальное — `signal()` в компоненте. Состояние фичи — класс-стор в `data/` с полями `signal` и `computed`, наружу `asReadonly()`: компонент читает, менять может только стор. Стор провайдится на уровне маршрута фичи, а не в `root`, — тогда при уходе со страницы состояние умирает вместе с ним, и выбранный файл на 10 МБ не висит в памяти. Глобальное клиентское — сигнал в `core/`, там только сессия и тосты.

**Состояние зоны загрузки — дискриминантное объединение, а не набор булевых флагов.** Четыре флага дают шестнадцать комбинаций, из которых валидны четыре, и компилятор не помогает. При объединении невозможно оказаться одновременно в `uploading` и `done`, а `progress` существует только там, где осмыслен.

**Умолчания:** `standalone`, `OnPush` на каждом компоненте, `input()` / `output()` вместо декораторов, все маршруты фич через `loadChildren`. RxJS — где есть поток событий во времени (прогресс, debounce), сигналы — для состояния.

**Именование:** в Angular 20 style guide отказался от суффиксов `.component` и `.service` в именах файлов и классов — `dropzone.ts` / `class Dropzone`. Важнее самой конвенции единообразие: смешанное именование агент воспроизводит хаотично, потому что видит в проекте оба образца.

### 6.2 Состояние: три вида, три инструмента

| Вид | Инструмент | Примеры |
|---|---|---|
| Серверное | TanStack Query | список файлов, профиль, квота |
| Локальное компонента | `signal()` | выбранный файл, состояние зоны, прогресс |
| Глобальное клиентское | сигнал в сервисе `core` | текущий пользователь, тосты |

**Серверные данные не копируются в сигналы.** Соблазн сделать `files = signal([])` и наполнять в `subscribe` — прямой путь к двум источникам правды и рассинхрону после удаления. После мутации инвалидируется ключ; квота (`['me']`) инвалидируется вместе со списком, иначе счётчик остаётся старым.

**NgRx не используется.** Глобального клиентского состояния два объекта — пользователь и тосты. Всё остальное серверное и живёт в Query. NgRx добавил бы actions, reducers, effects и selectors ради двух сигналов.

**TanStack Query подключается вместе с первым серверным списком** (страница файлов, спека 010), а не сразу. До этого момента серверных данных, которые нужно кешировать и инвалидировать, в приложении нет: конвертация — это одна мутация без кеша. Ставить библиотеку раньше — платить сложностью за задачу, которой ещё не существует.

### 6.3 Загрузка файла

```ts
this.http.post(`${base}/convert`, form, {
  responseType: 'blob',
  observe: 'events',
  reportProgress: true,
});
```

Три тонкости:

**`FormData` без ручного `Content-Type`.** Браузер проставит `multipart/form-data` вместе с boundary. Выставленный вручную заголовок теряет boundary, и сервер не разберёт тело — невнятная 400.

**Переход в «Конвертируем» по достижении 100% загрузки**, а не по `HttpEventType.Response`. Иначе пользователь несколько секунд смотрит на застывший прогресс-бар и думает, что зависло.

**Файл не читается в память.** `File` кладётся в `FormData` как есть; `FileReader` для отправки не нужен и на 10 МБ заметно бьёт по памяти.

### 6.4 Зона загрузки — конечный автомат

```
empty → dragover → selected → uploading → converting → done
  ↑         │          │           │           │         │
  └─────────┴──────────┴───────────┴───────────┴─── error
```

Восьмое состояние `quotaFull` выставляется до выбора файла по данным `['me']`.

**Мигание при `dragleave`.** Событие срабатывает при переходе курсора на дочерний элемент внутри зоны. Лечится счётчиком глубины `dragenter`/`dragleave`.

**Отмена возможна не везде.** Загрузку прервать можно — рвётся HTTP-запрос. Конвертацию нельзя: процесс уже идёт на сервере. Крестик в этом состоянии не показывается.

**На мобильных `dragover` не существует.** Зона превращается в кнопку над `<input type="file">`.

## 7. Аутентификация: сквозной поток

```
1. POST /auth/login
2. ← { accessToken } + Set-Cookie: refreshToken (HttpOnly, Secure, SameSite=Lax)
3. accessToken → сигнал в AuthService (в памяти, 15 минут)
4. При 401 → POST /auth/refresh (cookie уходит автоматически)
5. ← новый accessToken + новый refreshToken (ротация)
6. Повтор исходного запроса
7. Refresh не сработал → выход, редирект на /login
```

**Гонка при обновлении токена.** Если три запроса одновременно получили 401, наивная реализация вызовет `/auth/refresh` трижды. При ротации второй и третий вызов предъявят уже использованный токен, бэкенд сочтёт это кражей и завершит все сессии — пользователя выкинет из приложения без причины.

Решение на клиенте: очередь. Первый запрос обновляет, остальные ждут его результата.

Решение на сервере: короткое окно терпимости (несколько секунд) на повторное использование только что ротированного токена, либо блокировка по пользователю на время обновления.

## 8. Обработка ошибок сквозная

```
Backend                        Frontend
────────                       ────────
throw AppException(code)
        │
        ▼
AllExceptionsFilter
  code → { status, retryable }
  + request_id
        │
        ▼
  problem+json  ──HTTP──▶  errorInterceptor
                                 │
                                 ▼
                            AppError { code, message, requestId, retryable }
                                 │
                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
                зона загрузки  тост       баннер
```

Компоненты работают только с `AppError` и никогда не разбирают сырой `HttpErrorResponse`.

| Категория | Где показывается |
|---|---|
| Файл отклонён, квота исчерпана | В зоне загрузки |
| Rate limit, таймаут, сбой конвертера | Тост |
| Сервис недоступен | Баннер над содержимым |
| Ошибка поля формы | Инлайн под полем |

Тексты берутся из i18n-словаря по коду ошибки, а не приходят с бэкенда: серверный `detail` на английском и адресован разработчику. Текст содержит числа и способ решения, а не «Ошибка загрузки».

`request_id` генерируется на клиенте, передаётся в заголовке, попадает в лог бэкенда и возвращается в ошибке — сквозная трассировка одного запроса.

## 9. Режимы отказа

| Сценарий | Последствие | Что делаем |
|---|---|---|
| Файл загружен в хранилище, вставка в БД упала | Объект без ссылки занимает место вечно | Фоновая сверка раз в сутки: перебрать ключи, сопоставить с `files`, удалить лишние старше 24 часов |
| Транзакция прошла, `storage_used_bytes` разошёлся | Квота считается неверно | Ночная сверка: пересчёт `SUM(size_bytes)` по пользователям |
| Gotenberg не отвечает | Конвертация документов недоступна | Таймаут, `CONVERSION_TIMEOUT`, изображения продолжают работать |
| Пул конвертации заполнен | Запросы копятся | Ожидание до 10 с, затем `503` + `Retry-After` |
| Redis недоступен | Rate limit не работает | Fail-open для лимитов, fail-closed для сессий: отсутствие проверки частоты допустимо, отсутствие проверки токена — нет |
| Объектное хранилище недоступно | Нельзя сохранять и скачивать | `503 STORAGE_UNAVAILABLE`, баннер в интерфейсе |
| Клиент оборвал соединение при загрузке | Временный файл остался | Удаление в `finally` |
| Повторная отправка формы | Две одинаковые конвертации | Блокировка кнопки на клиенте + `Idempotency-Key` на сервере |

## 10. Развёртывание

```
        Vercel                    Railway                 Cloudflare
   ┌──────────────┐    ┌───────────────────────────┐   ┌────────────┐
   │  Angular     │───▶│  api (Dockerfile)         │──▶│  R2 bucket │
   │  статика CDN │    │  gotenberg (без домена)   │   │            │
   └──────────────┘    │  postgres (managed)       │   └────────────┘
                       │  redis (managed)          │
                       └───────────────────────────┘
```

Переменные окружения задаются на площадке, в репозиторий не попадают. Railway подставляет значения между сервисами: `DATABASE_URL=${{Postgres.DATABASE_URL}}`, `GOTENBERG_URL=http://${{gotenberg.RAILWAY_PRIVATE_DOMAIN}}:3000`.

Миграции применяются при старте контейнера (`prisma migrate deploy`). Для проекта такого размера это нормально; при нескольких инстансах их выносят в отдельный шаг деплоя, чтобы миграции не запускались одновременно.

**Три частые ошибки:** Output Directory для Angular — `dist/web/browser`, а не `dist/web`; `CORS_ORIGIN` — конкретный домен, потому что `*` с `credentials` не работает; Gotenberg не получает публичный домен.

### Локальная разработка

Фронтенд-фаза (стадии 0–3, `TECH-SPEC.md` §14) — без Docker и без `apps/api`:

```bash
pnpm --filter shared build
pnpm --filter web dev
```

Бэкенд-фаза (стадия 4 и далее) добавляет API и инфраструктуру:

```bash
docker compose up -d       # postgres, redis — со стадии 4
pnpm --filter shared build
pnpm --filter api dev
pnpm --filter web dev
```

До стадии 10 хранилище — `LocalDiskStorage`, `docker-compose.yml` поднимает только postgres и redis. На стадии 10 в тот же compose добавляются gotenberg и minio, `docker compose up -d` не меняется, меняется только состав сервисов.

Приложения запускаются вне контейнеров ради горячей перезагрузки. `healthcheck` у postgres и redis обязателен: без него `depends_on` не дождётся готовности, и API упадёт при старте.

## 11. Тестирование

| Уровень | Инструмент | Что покрывает |
|---|---|---|
| Unit | Vitest | 🔒-валидаторы, автомат зоны загрузки, pipes, расчёт квоты, `formatBytes`/`formatDate` |
| Интеграционные / e2e бэкенда | Vitest + `supertest` поверх `AppModule` | Транзакции квоты, миграции, `problem+json`, коды ошибок — на настоящем PostgreSQL (`convert_hub_test`) |
| E2E браузера | Playwright (chromium) | Конвертация от выбора файла до скачивания, вход, отказ по размеру, квота |

**Настоящий PostgreSQL, а не in-memory база.** SQLite или H2 ведут себя иначе на транзакциях, частичных индексах и типах — тесты проходят, прод падает. Testcontainers из первоначального плана заменён (решение владельца, `specs/015-testing.md`) второй базой `convert_hub_test` на том же контейнере `postgres`, что и dev: тот же образ и версия, без Docker-in-Docker на CI. Изоляция — каждый тест удаляет за собой созданные строки, не глобальный rollback.

Обязательный e2e-минимум перед деплоем (Playwright, `apps/web/e2e/`): гость конвертирует файл; пользователь входит и видит файл в хранилище; файл больше 10 МБ отклоняется; при заполненной квоте конвертация проходит, но файл не сохраняется.

## 12. Что менять при росте нагрузки

Порядок именно такой — каждый шаг делается, когда упёрлись, а не заранее.

1. **Горизонтальное масштабирование API.** Приложение stateless, состояние в Postgres и Redis. Добавляется реплика.
2. **Отдельный пул Gotenberg.** Несколько экземпляров за балансировщиком, если документы становятся узким местом.
3. **Переход на асинхронную модель.** Очередь (BullMQ на Redis) и воркеры — при выполнении условий из TECH-SPEC, п. 4.
4. **CDN перед хранилищем.** Если скачивания начинают доминировать.
5. **Реплика БД для чтения.** Список файлов и история уходят на неё.

Первые три шага не требуют изменения архитектуры — только конфигурации и, для третьего, замены синхронного вызова на постановку в очередь внутри `conversion.service.ts`. Границы из раздела 2 сохраняются на всех шагах.

## 13. Куда положить новый файл

```
Zod-схема или константа, которую видят обе стороны?
  └─ да → packages/shared

Серверный код?
  ├─ относится к одной фиче?        → apps/api/src/modules/<фича>/
  ├─ инфраструктура для всех фич?   → apps/api/src/common/
  └─ конфигурация окружения?        → apps/api/src/config/

Клиентский код?
  ├─ относится к одному разделу?    → apps/web/src/app/features/<раздел>/
  ├─ переносимо в другой проект?    → apps/web/src/app/shared/
  └─ один экземпляр на приложение?  → apps/web/src/app/core/
```

Ответ «относится к двум фичам» — не повод импортировать вбок. Либо код общий и уезжает уровнем ниже, либо границы фич проведены неверно, и это обсуждается до написания кода.

**Ограничения `packages/shared`:** никаких зависимостей от `@nestjs/*` и `@angular/*`, только `zod` и стандартная библиотека; никакого `process.env` — иначе пакет не соберётся в браузере; коды ошибок — `as const`-объект, а не `enum`, нужен тип-объединение строковых литералов для сужения на фронте.

Проверка, что общий пакет работает: измените лимит с 10 МБ на 8 МБ — фронтенд должен **перестать компилироваться** там, где значение захардкожено. Собралось молча — дубль остался.
